# 任务：对接用户注册与登录

你是一名资深 React + TypeScript 前端工程师。请在当前前端项目中对接已完成的用户认证后端，实现注册、登录、退出、登录态恢复、受保护路由和资料修改。先阅读现有路由、状态管理和 API 封装，沿用它们，不要另起一套请求库或状态库。

后端是 AI 定制服装商城，本地默认 `http://localhost:8080`。认证使用服务端 Session，会话 ID 只存在 HttpOnly Cookie 里。前端不能读写这个 Cookie，也不能把 Session ID 或任何长期凭证写入 `localStorage`、`sessionStorage` 或内存以外的持久存储。

登录是否有效，只以 `GET /api/v1/auth/me` 的结果为准。本地缓存的用户对象只能做展示，刷新后必须重新向服务端确认。

## 一、请求约定

- 所有接口前缀：`/api/v1`
- `Content-Type: application/json`
- 跨域时每个请求都带 `credentials: "include"`（axios 为 `withCredentials: true`）
- 请求体只包含下面列出的字段。多一个字段会返回 400，`code` 为 `INVALID_ARGUMENT`，`message` 为「请求包含不支持的字段」
- 请求体上限约 8KB。格式不是合法 JSON、或 JSON 后面还有多余内容，返回 400，「请求格式不正确」
- 不要在 URL、日志、错误上报里放密码
- 不要传 `user_id`。当前用户只由 Cookie 里的会话决定
- 写接口如果浏览器带了 `Origin`，该来源必须在后端允许列表中，否则 403，`code` 为 `FORBIDDEN`，`message` 为「来源不被允许」

本地默认允许的前端来源是 `http://localhost:5173`。开发服务器请用这个源，或让后端把实际源加进 `CORS_ALLOWED_ORIGINS`。后端不会对 `*` 放行，带 Cookie 时也不能配成允许任意来源。

同源部署时同样要让浏览器带上 Cookie。Cookie 名默认 `session_id`，`Path=/`，`HttpOnly`，本地 `SameSite=Lax`、`Secure=false`，有效期默认 168 小时。前端不要自己写这个 Cookie。

## 二、统一响应

成功 HTTP 200：

```json
{
  "code": "OK",
  "message": "success",
  "data": {}
}
```

失败时 HTTP 状态码表达错误类别，`data` 固定为 `null`：

```json
{
  "code": "UNAUTHENTICATED",
  "message": "请先登录",
  "data": null
}
```

按 `code` 分支，把 `message` 直接展示给用户。不要根据 HTTP 状态码单独发明另一套文案。

| HTTP | code | 何时出现 | message |
| --- | --- | --- | --- |
| 400 | INVALID_ARGUMENT | 字段、格式或取值不合法 | 见下文各条校验文案 |
| 401 | UNAUTHENTICATED | 未登录、会话失效，或登录账号/密码错误 | 「请先登录」或「账号或密码错误」 |
| 403 | FORBIDDEN | 已登录但账号停用，或跨域来源不在允许列表 | 「账号已停用」或「来源不被允许」 |
| 409 | CONFLICT | 邮箱或手机号已注册 | 「该邮箱或手机号已注册」 |
| 429 | RATE_LIMITED | 注册或登录过于频繁 | 「尝试次数过多，请稍后再试」 |
| 500 | INTERNAL | 未预期的服务端错误 | 「内部错误」 |
| 503 | UNAVAILABLE | Redis 或会话不可用 | 「服务暂时不可用」；注册时若账号已写入但会话没建成，为「账号已创建，会话暂时不可用，请稍后登录」 |

时间字段是 UTC 的 RFC3339 字符串。

用户公开资料 `data`：

```json
{
  "id": 1,
  "nickname": "测试用户",
  "avatar_url": null,
  "status": "active",
  "last_login_at": "2026-10-27T09:00:00Z",
  "created_at": "2026-10-27T09:00:00Z"
}
```

- `id` 是数字
- `avatar_url` 没有头像时为 `null`
- `status` 目前为 `active` 或 `disabled`。登录接口不会把停用账号放进来；访问受保护接口时停用账号得到 403
- `last_login_at` 可能不出现
- 响应里没有密码、密码哈希、邮箱、手机号。个人中心若要展示登录账号，需要用户自己记住，或等后续接口，不要从响应里猜

## 三、字段规则

`identity_type` 只能是 `email` 或 `phone`。服务端会去掉首尾空白并转成小写。

邮箱：

- 去掉首尾空白后转小写再提交也可以，服务端会再做一次
- 最长 128
- 需匹配常见邮箱形式
- 不合法时 message 为「邮箱格式不正确」

手机号只支持中国大陆手机号：

- 最终是 `1[3-9]` 开头的 11 位数字
- 可以带空格、短横线；`+86`、`86`、`0086` 前缀会被去掉
- 其他国家号码不支持
- 不合法时 message 为「手机号格式不正确」
- 身份类型不是 email/phone 时 message 为「身份类型只支持 email 或 phone」

密码：

- 至少 8 个字符（按 Unicode 字符计）
- 不超过 72 字节
- 不合规时 message 为「密码至少 8 个字符，且不超过 72 字节」
- 登录失败不区分账号不存在、密码错误、账号停用，一律「账号或密码错误」

昵称：

- 去掉首尾空白后 1 到 64 个字符
- 不能含控制字符
- 不合规时 message 为「昵称长度需为 1 到 64 个字符」或「昵称不能包含控制字符」

头像：

- 必须是带主机名的 `http` 或 `https` URL
- 不能有空格或换行，最长 512
- 不能带 URL 用户信息（`user:pass@host`）
- 不合规时 message 为「头像地址不正确」
- 当前接口不能把头像清空。省略 `avatar_url` 或传 `null` 表示不修改

注册只校验格式，不验证邮箱或手机号归本人所有。注册页需明确提示：当前注册不会校验收据真实性。

## 四、接口

### 1. 注册

`POST /api/v1/auth/register`

```json
{
  "nickname": "测试用户",
  "identity_type": "email",
  "identifier": "test@example.com",
  "password": "password1"
}
```

成功时 `data` 为用户公开资料，并 `Set-Cookie`。注册成功即已登录，不要再自动调一次登录。

同一邮箱或手机号重复注册返回 409。若返回 503 且 message 为「账号已创建，会话暂时不可用，请稍后登录」，账号已经存在，应引导去登录，不要提示用户再注册一次。

同一 IP 注册限流为每小时 20 次，超限 429。参数错误也会消耗额度。

### 2. 登录

`POST /api/v1/auth/login`

```json
{
  "identity_type": "email",
  "identifier": "test@example.com",
  "password": "password1"
}
```

成功时 `data` 为用户公开资料，并写入新的会话 Cookie。旧会话作废。

登录限流：同一 IP 每 15 分钟 30 次，同一身份（类型 + 规范化后的邮箱或手机号）每 15 分钟 10 次。参数错误同样计数。收到 429 时禁用提交并展示 message，不要立刻重试。

### 3. 退出

`POST /api/v1/auth/logout`

无请求体。成功时 `data` 为 `{}`，并清除 Cookie。未登录时再调一次也应成功。

若返回 503，Cookie 可能已经被清掉，前端仍应清空内存中的用户状态；可以提示「服务暂时不可用」，不要把本地用户继续当成已登录。

### 4. 当前用户

`GET /api/v1/auth/me`

必须已登录。成功时 `data` 为用户公开资料。

未登录或会话失效：401，「请先登录」。服务端会清掉无效 Cookie。Redis 不可用：503，「服务暂时不可用」，此时不要当成未登录去清掉用户又立刻循环跳转；可以展示服务不可用，并允许用户稍后重试。

### 5. 修改资料

`PATCH /api/v1/users/profile`

只提交要改的字段。两个字段都可以省略；都省略时返回当前资料，不报错。

```json
{ "nickname": "新昵称" }
```

```json
{ "avatar_url": "https://cdn.example.com/a.png" }
```

不能提交 `id`、`status`、`last_login_at`、`created_at` 或其他字段。未登录 401。账号已停用 403，并清除 Cookie。

## 五、页面与状态

至少完成这些流程：

1. 注册页：昵称、身份类型（邮箱 / 手机号）、登录标识、密码。提交成功后进入已登录状态，用户数据用响应里的 `data`。
2. 登录页：身份类型、登录标识、密码。成功后同样写入当前用户。
3. 应用启动和页面刷新时调用 `/api/v1/auth/me`。200 则恢复用户；401 则视为未登录。恢复完成前，受保护页面不要先闪一帧内容再跳走。
4. 未登录访问受保护页面时进入登录页，并记住来源，登录成功后回到该页面。
5. 退出后清空前端用户状态，再进入登录页或首页。
6. 资料修改成功后用响应 `data` 替换当前用户。
7. 401 出现在已登录后的业务请求上时，清空用户状态并进入登录页。403 且 message 为「账号已停用」时同样退出登录态，并展示该文案。

表单在浏览器侧做同样的长度和格式校验，减少无效请求，但服务端 message 仍是最终提示。提交中禁用按钮，防止重复注册或触发限流。

密码框使用 `type="password"`。不要把密码放进路由、全局状态或错误日志。

## 六、不要做的事

- 不要实现收货地址、验证码、忘记密码、第三方登录。后端没有这些接口。
- 不要用前端保存的用户 id 调用「按 id 查用户」一类接口。
- 不要解析或转发 `Set-Cookie`。浏览器会自己保存 HttpOnly Cookie。
- 不要为了跨域去改成 Bearer Token。
- 不要引入与项目现有路由、请求封装重复的依赖。
- 不要把未实际跑通的页面说成已经对接完成。

## 七、自测

后端需已启动，且 CORS 允许当前前端源。然后确认：

1. 邮箱注册成功，随后刷新，`/auth/me` 仍返回同一用户。
2. 同一邮箱再注册得到 409。
3. 非法邮箱、非法手机号、非法身份类型、过短密码在提交前或接口返回中被拦住。
4. 错误密码与不存在的账号都显示「账号或密码错误」。
5. 退出后刷新，`/auth/me` 为 401，受保护页面进入登录页。
6. 开发者工具里会话 Cookie 为 HttpOnly，Application 的 Local Storage 中没有会话 ID。
7. 修改昵称成功；请求体里夹带 `status` 时接口拒绝，页面上的账号状态不变。
8. 跨域环境下请求带 Cookie，且没有 CORS 报错。
