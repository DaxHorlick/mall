# 任务：将独立服装设计器 Demo 整合到现有电商项目

## 一、项目背景

当前项目是一个 AI 定制服装电商平台，采用前后端分离架构。

主体项目已经具备基础业务模块，服装设计器也已经作为一个独立 Demo 开发完成。

现在需要将独立设计器 Demo 整合到主体项目中，使其成为正式业务模块，而不是继续作为独立项目运行。

本次任务的核心是代码整合，不是重新开发设计器。

## 二、整合目标

将独立设计器的功能完整迁移到主体项目，要求：

1. 保留 Demo 已经实现的设计器功能。
2. 适配主体项目现有的前端技术栈。
3. 统一主体项目的路由管理。
4. 统一主体项目的 UI 组件和样式规范。
5. 接入主体项目现有的用户认证体系。
6. 为后续 Go 后端接口和数据库接入预留合理结构。
7. 不影响主体项目现有功能和业务模块。

## 三、首先分析两个项目

在修改代码之前，先检查主体项目和设计器 Demo。

重点分析：

### 主体项目
- package.json
- src 目录结构
- 路由管理方式
- UI 组件库
- 状态管理方式
- HTTP 请求封装
- 用户认证方式
- 全局 CSS 和 Tailwind 配置
- 项目构建配置

### 设计器 Demo
- package.json
- 页面入口
- 组件结构
- Three.js / React Three Fiber 使用方式
- GLB 模型加载方式
- Canvas / Konva 图案编辑方式
- 图层管理方式
- 图片上传与预览方式
- Zustand 或其他状态管理方式
- 静态资源及模型文件
- 样式和第三方依赖

分析两个项目之间的依赖差异和代码冲突。

## 四、代码整合要求

### 1. 页面整合

将设计器作为主体项目中的独立业务页面。

建议路由：

/designer

后续支持：

/designer/:designId

不要保留 Demo 原来的独立应用入口和独立路由体系。

### 2. 组件整合

将设计器相关组件放入主体项目合理的业务目录。

建议结构：

src/
modules/
designer/
pages/
DesignerPage.tsx
components/
Canvas2D/
Preview3D/
LayerPanel/
Toolbar/
PropertyPanel/
hooks/
stores/
services/
types/
utils/
assets/

根据主体项目现有目录规范适当调整，不要为了套用这个结构破坏原有架构。

### 3. 3D 资源整合

确保以下资源能够正常加载：

- GLB 模型
- UV 模板
- 材质贴图
- 其他模型资源

检查资源路径，避免 Demo 中使用的相对路径在主体项目中失效。

模型资源应统一管理，不要随意复制多份。

### 4. 状态管理整合

设计器内部的状态可以独立管理，但需要考虑主体项目的用户和业务状态。

需要区分：

- 当前用户信息：使用主体项目现有认证状态。
- 当前设计作品：由设计器模块管理。
- 当前图层：由设计器模块管理。
- 当前模型：由设计器模块管理。
- 当前设计版本：为后续持久化预留。

不要重复创建用户认证、登录状态或全局请求管理。

### 5. 样式整合

- 统一主体项目的字体和颜色规范。
- 统一 UI 组件使用方式。
- 避免 Demo 的 CSS 污染主体项目其他页面。
- 保留设计器自身合理的专业编辑器布局。
- 不要为了统一风格而破坏原有设计器交互体验。

### 6. 后端接口预留

本次不要求实现数据库和 Go 后端接口。

但需要将设计器业务逻辑与页面组件分离。

为以下功能预留 service：

- createDesign
- getDesign
- updateDesign
- saveDesignVersion
- uploadDesignAsset

当前可以使用 Mock 数据完成页面运行，不要伪造已经接入后端的功能。

## 五、重要约束

1. 不要重新开发已经完成的设计器功能。
2. 不要删除主体项目已有业务模块。
3. 不要覆盖主体项目原有 package.json 配置。
4. 不要随意升级 React、Three.js 等依赖版本。
5. 不要重复安装已有依赖。
6. 不要将 Demo 中的用户认证体系迁移进来。
7. 不要修改与本次整合无关的业务代码。
8. 不要擅自修改 GLB 模型和 UV 映射。
9. 保留现有 Demo 的核心交互和视觉效果。

## 六、执行流程

第一步：分析主体项目与 Demo 的代码结构和技术依赖。

第二步：输出整合方案，包括：
- 需要迁移的文件
- 需要修改的文件
- 需要新增的文件
- 依赖冲突及解决方式
- 路由整合方案
- 资源迁移方案

第三步：按照整合方案实际执行代码迁移。

第四步：运行项目并修复问题。

第五步：验证：
- 主体项目正常启动。
- 原有页面正常访问。
- /designer 可以正常打开。
- GLB 模型正常加载。
- 2D 图案编辑正常。
- 3D 实时预览正常。
- 原有登录认证正常。
- 页面切换不会出现样式污染或状态冲突。

## 七、最终交付

完成代码整合后，输出：
1. 新增文件清单。
2. 修改文件清单。
3. 新增依赖清单。
4. 新的路由地址。
5. 已完成的功能。
6. 尚未完成的问题。
7. 后续接入 Go 后端需要的接口。

现在先检查两个项目，确认实际目录和技术栈，然后制定并执行整合方案。不要在没有分析代码之前直接大规模修改。
